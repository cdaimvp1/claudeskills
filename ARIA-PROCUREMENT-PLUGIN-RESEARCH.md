# ARIA Procurement Plugin + Skills-as-Recipes — Feasibility & Approach (research)

# Feasibility + Approach: A `procurement` Plugin for ARIA that Runs Lilly Skills as Recipes

## 1. How ARIA works

ARIA is not a separate agent. It is Claude itself, running inside Claude Desktop, driven by one large skill file (`aria.skill`) plus ~130 MCP tools served by a local unified Python process (`main.py --server aria`). The split is deliberately hybrid. The LLM (Claude, client side) is the only reasoning engine in the standard flow: it reads the stage methodology (E1 Understand through E5 Interpret), grounds itself in Canon (a 15 table metadata catalog read via deterministic DuckDB queries in a mandatory Phase 0), decides which data path or recipe to use, authors DAX/SQL when nothing fits, verifies, and composes output. Underneath it, three co-located MCP servers (`aria_session`, `aria_data`, `aria_compute`) do all real I/O in plain Python/SQL/DAX with no LLM in the loop. A second LLM appears only inside one optional plugin (`aia`, Claude on Bedrock doing server-side NL to query over claims data), and ARIA treats that class as explicitly non-deterministic.

Plugins and recipes play different roles. A **plugin** is a single `.py` module under `plugins/` that adds MCP *tools* (the deterministic execution surface): metadata constants (`PLUGIN_NAME/VERSION/TOOLS`, etc.) plus a `register(mcp, conn_manager)` that registers each capability as an `@mcp.tool`-decorated closure named `aria_<plugin>_<verb>`, whose docstring (WHEN TO USE / WORKFLOW / GOTCHAS) is the spec Claude reasons over. A **recipe** is a markdown file with YAML frontmatter that *orchestrates* those tools for a specific analytical question. It has two layers: a human `tool_plan:` prose block that Claude dispatches step by step with reasoning, and an optional machine `plan:` array that `aria_pull_recipe` executes deterministically with `{PARAM}` substitution, in parallel, no LLM per step. Crucially, `aria_pull`'s executor supports only three step kinds today (`fabric_dax`, `fabric_measure`, `cache_query`); anything else (SAP, SAC, SEC, and by extension a new procurement plugin) is a "deferred kind" that a recipe cannot auto-execute. Those must be orchestrated narratively: the recipe drops the `plan:` block, sets `recipe_kind: tool_orchestration`, and its prose teaches Claude to call the plugin tools directly in sequence, binding one step's output into the next (exactly what `sec_brand_revenue_from_8k` does).

The **venv tiers are an install-readiness mechanism, not capability or model tiers.** Tier 1 (~35MB, session + Canon + auth), Tier 2 (~95MB, data + core plugins, pandas/pyarrow class), Tier 3 (~80MB, forecasting ML, torch/gluonts). A background daemon fetches each tier in parallel and drops sentinel files; all tools are advertised at t=0, and calling a tool whose tier is not yet ready returns a `tier_pending_error` retry envelope. This matters for us only as a packaging decision: a procurement plugin that reuses Fabric's already-installed duckdb/pyarrow adds no new tier weight; one that vendors heavy deps would.

## 2. Recommended integration architecture

**Shape: one optional `procurement` plugin (deterministic tool surface) + one recipe per skill (orchestration). This mirrors the existing `sec` + `sec_*` recipes pattern exactly and is the only shape ARIA's primitives actually support.** ARIA has no first-class "recipe registry" a plugin can declare; recipes are Canon content, plugins are tools. So the plugin exposes *capabilities* and each skill's workflow lives in a recipe that calls them.

**What the plugin exposes (capabilities):** the deterministic cores lifted from the Lilly skills. The single highest-value asset is `lilly-procurement-kernels-1c344a/numeric_kernel.py` (8 pure, typed, refusal-based, unit-tested, stdlib-only functions: `to_hourly`, `convert_currency`, `percentile_gate`, `verify_line_math`, `escalate`, `weighted_score`, `npv`, `quadrature_rollup`) already vendored byte-identical into 10 skills, plus the six skill-specific kernels (`assign_tier`, `compute_chain`, comment strip/finalize, `compute_complexity_score`, roster classify, and the `generate_pro_forma_workbook` XLSX generator). These are essentially plugin-ready as-is. Expose each as an `aria_procurement_<verb>` tool with the standard 4-key annotation block (`readOnlyHint: True` throughout, per ARIA's and Theo's reflect-don't-enforce lock), a try/except envelope returning `{"success": bool, ...}` with `hint` and ranked `suggested_*` on failure, and byte-budget response shaping for large results (or Parquet cache + receipt for tabular pulls).

**What a skill-recipe looks like:** frontmatter (`recipe_id`, `applies_to_sources` including `procurement_plugin` and any Fabric source, typed `parameters:`, `discovery_keywords:`, `harness_assertions:`, reused `related_canon_rules:`) plus a body carrying the skill's actual logic as the prose Claude executes. The `supplier_landscape` template in the research is the canonical example: a deterministic Fabric DAX pull for spend concentration in `plan:`, then narrative steps that call the new plugin tools and apply the skill's scoring rubric.

**Resolving the core tension** (ARIA recipes/plugins are deterministic; Lilly skills are LLM-driven SKILL.md workflows). There is no single answer; each of the three options fits a different class of skill:

- **Option A, skill-as-pure-recipe (no code):** the SKILL.md's shared block + workflow becomes a retrieval-grounded prompt template; ARIA's own LLM + Canon retrieval run it. Fits chat-only, no-kernel, no-dashboard skills. This is a plain `tool_orchestration` or methodology recipe with behavior-anchored assertions.
- **Option B, recipe-calls-plugin-wrapping-deterministic-kernels:** the numeric/decision-table sub-steps become plugin tool calls; the LLM does only sourcing, classification, and narrative. This is the strongest, lowest-risk, highest-correctness option because the kernels are already isolated, typed, refusal-based, and independently tested. It is also a correctness *upgrade* over the skills' own weaker "LLM-authored JSX arithmetic" (supplier-landscape), because a plugin call is independently verifiable where generated JSX is not. Fits every kernel-backed skill's numeric spine.
- **Option C, plugin-invokes-an-LLM-tier to run the whole SKILL.md:** required where the "logic" *is* natural-language judgment (multi-pass web research funnels, DOCX tracked-changes XML manipulation, persona-driven redlines). This is the hardest and least native: ARIA has no built-in `create_file`/`web_fetch`/docx-XML equivalent inside a plugin, and running a non-deterministic mega-prompt inside a tool call breaks the deterministic-tool contract. In practice this collapses into Option A + B: the *surrounding judgment* runs as ARIA's client-side LLM following recipe prose (the G2/G7/G8 gates re-expressed as recipe steps), and only the arithmetic contracts out to plugin tools. A true server-side "run the SKILL.md" plugin tier is possible but is a build, not a wiring exercise, and should be deferred.

**Most real skills are hybrid B+C** (should-cost-builder and lilly-contract-review both do heavy LLM research/classification *and* hard-require kernel calls). The right default is: LLM judgment lives in the recipe body Claude executes; hard arithmetic and decision tables live in plugin tools; nothing writes back to a system of record.

## 3. Skill to recipe mapping (~29 skills)

**Easy / mostly-deterministic core (Option B, kernel-backed, 16 skills)** — deterministic spine already isolated as tested Python; wrapping it is near-mechanical extraction. Exposed as: plugin tools for the kernel functions + a recipe per skill whose body calls them and reasons around them.
- Cleanest wins (isolated tested refusal-based core): **pro-forma-builder** (full mechanical XLSX generator with Python-vs-formula reconciliation, the most mechanized deliverable), **market-rate-benchmarking**, **should-cost-builder**, **invoice-rate-card-auditor**, **timeline-builder**, **workflow-map**, **evaluation-engine**, **legal-negotiation-prep**, **executive-summary-package**, **comment-cleanup**.
- Also kernel-backed but heavier LLM shell: commercial-negotiation-prep, deal-room, rfp-response-analysis, scope-sow-architect, sole-source-challenge, and lilly-contract-review (kernel covers only the arithmetic sub-step; overall this is a hard skill, see below).

**Pure-recipe candidates (Option A, no code, 4 skills):** procurement-help-desk (chat-only, structured cited answer, has a prompt-injection guard to preserve), process-navigator, meeting-prep-brief, voice-profile. Exposed as retrieval-grounded prompt-template recipes; no plugin dependency.

**Hard / mostly-LLM reasoning (Option C, high judgment / document-XML / multi-pass research, ~9 skills):** lilly-contract-review (redlined-DOCX tracked-changes production, playbook + persona reasoning), supplier-landscape (10-15→5→10 vendor research funnel, *no kernel at all*), category-strategy, negotiation-simulator, rfp-engine, rfp-case-manager, supplier-deep-dive, theos-field-guide, procurement-launcher (the THEO orchestrator itself), negotiation-playbook-learning. Exposed as `tool_orchestration` recipes that encode the gate discipline as prose, chaining any available deterministic tools (Fabric spend, `aria_forecast_*`, the numeric kernels) but leaning on ARIA's client-side LLM for the judgment. These are where ARIA is missing primitives (see gaps) and where I would not promise fidelity in an MVP.

**Free today, zero new code:** anything expressible as Fabric DAX/measure against the already-wired `S2P Purchase Order Product` source. Baseline spend/vendor/PO-aging analytics already ship as `procurement_spend_summary`, `s2p_open_po_aging`, `s2p_vendor_spend_top_n`. More such recipes are pure authoring.

## 4. What it would take

**Build steps.**
1. Extract the shared numeric kernel + 6 skill kernels into `plugins/procurement.py`. Because they are stdlib-only and dependency-free, this is close to a copy-in behind `@mcp.tool` closures. Keep `PLUGIN_DEPENDENCIES = []`.
2. Write docstrings per the fixed rubric (one-line keyword header → prose → Args → Returns envelope → WHEN TO USE → WORKFLOW Before/After/Instead → GOTCHAS), cross-referencing `aria_fabric_*` and `aria_forecast_*` where procurement chains into spend/forecast.
3. Wrap every body in try/except returning `{"success": bool, ...}`; add byte-budget shaping for large returns and the Parquet-cache-plus-receipt pattern for tabular pulls (the natural handoff point for the skills' existing `*_handoff.json` objects).
4. Add the `PLUGIN_CATALOG.json` entry (`category: "optional"`, install note, sha256 for OTA).
5. Author recipes per skill under `content_cache/recipes/`, reusing `s2p_*` and the `supplier_landscape` template; reuse existing S2P gotcha rules (`s2p_gotcha_intercompany_inclusion`, `unfiltered_spend`, `spend_exclusions`) rather than re-authoring.
6. Ship through Canon Builder review + harness validation, then promote to OneLake; recipes sync to every install at next session open with no ARIA redeploy.

**Plugin spec (skeleton):** `PLUGIN_NAME="procurement"`, `PLUGIN_VERSION="1.0.0"`, `PLUGIN_MIN_ARIA="17.0.0"`, `PLUGIN_AUTHOR="<owner>@lilly.com"`, `PLUGIN_DEPENDENCIES=[]`, `PLUGIN_TRUST_TIER="beta"` initially, `PLUGIN_TOOLS=[...]` matching every registered `@mcp.tool`. One `register(mcp, conn_manager=None)` with tools like `aria_procurement_verify_line_math`, `aria_procurement_quadrature_rollup`, `aria_procurement_npv`, `aria_procurement_weighted_score`, `aria_procurement_percentile_gate`, `aria_procurement_escalate`, `aria_procurement_assign_tier`, `aria_procurement_compute_chain`, `aria_procurement_complexity_score`, `aria_procurement_generate_pro_forma`.

**Sample recipe (abbreviated):** the `supplier_landscape` recipe from the research is the working template: `recipe_kind: tool_orchestration`, typed params (`CATEGORY`, `FISCAL_YEAR`, `TOP_N_SUPPLIERS`), a deterministic `fabric_dax` step for third-party spend concentration (reusing `s2p_vendor_spend_top_n`'s DAX shape with the mandatory Fiscal Year filter and the P/A intercompany exclusion), then narrative steps calling `aria_procurement_*` tools per top-N vendor and applying the landscape scoring rubric, a markdown `output:` contract mirroring the skill's dashboard sections, reused `related_canon_rules`, `canonical_params`, and mixed `harness_assertions` (`row_count_min` for the deterministic half, `content_includes` for the narrative half).

**Auth / data / credentials.** Follow ARIA's three observed patterns. For the pure-kernel tools there is no external system and no credential at all (they are math over inputs Claude already holds). For spend data, reuse the existing Fabric path via `conn_manager.get_connection(source_id)` and the `@require_canon`/`@require_valid_session` decorators pulled off `aria_data.server` inside `register()` — no new SSO. Only if a skill needs a net-new system (Ariba, ServiceNow, Aravo, a CLM/contract repository, market feeds) does credential work appear, and per the locked cross-cutting rules those systems are governed human-confirmed writes, never autonomous, so they stay out of scope. **Venv tier:** reuse Fabric's already-installed duckdb/pyarrow so procurement adds no new tier weight; do not vendor heavy deps into the plugin. If a lazy-tier probe is ever needed, do it once at plugin-activate, not per-call (the forecasting.py FB-020 lesson: per-call import probing cost ~240s cold start).

**Gaps / risks.**
- **Running an LLM skill deterministically is not possible, and pretending otherwise is the main risk.** The hard skills' value is multi-pass judgment; a deterministic tool cannot reproduce it. Option C degrades to "ARIA's client LLM follows recipe prose," which loses the skills' own gate enforcement (G7 research minimums, G8 pass-artifact discipline) unless those are re-expressed as recipe steps and checked by behavior-anchored assertions. Fidelity will be lower than the native skill.
- **Missing primitives.** ARIA plugins have no equivalent of Claude's `create_file`, `web_fetch`, `visualize:show_widget`, or docx `unpack.py`/tracked-changes XML tools. lilly-contract-review (reads `word/comments.xml`, emits `<w:ins>`/`<w:del>`) and any DOCX/dashboard deliverable cannot be reproduced through the plugin/recipe surface today.
- **Data grounding.** Recipes are only as good as reachable data. Spend/vendor/PO analytics are free because Fabric is wired; skills needing Ariba/ServiceNow/Aravo/CLM block on a plugin build first, and those are governance-restricted.
- **Output formats.** ARIA's output contract is markdown/excel/chart via `aria_compose_dashboard`; the skills emit DOCX/XLSX/JSX bundles + handoff JSON. Only the tabular/markdown and XLSX (via `generate_pro_forma`) portions map cleanly. Dashboards do not port — the skills' dashboards are LLM-authored JSX artifacts, and supplier-landscape's "derived in code" score is unverified generated JavaScript, not an executed function. Moving that arithmetic into `aria_procurement_weighted_score` is a correctness gain but the visual dashboard itself is out of scope.
- **Executor limitation:** `aria_pull`'s `_SUPPORTED_KINDS` is a fixed 3-item set. No procurement plugin tool can be an auto-executed `plan:` step; all plugin chaining is narrative `tool_orchestration`. Recipe authors cannot add a step kind — that is a core-server change.
- **Catalog drift** is tolerated by design (the `sec` catalog `tools` list does not match its registered tools); treat in-module `PLUGIN_TOOLS` + decorators as truth, the catalog as an advertising/installer manifest.
- **Unresolved contract question:** none of the plugins read implement a native "recipe registration" surface; whether ARIA core supports a `run_recipe(name)` dispatch tool (option 2 in the plugin-contract findings) versus one-tool-per-skill (option 1) requires reading the core loader/`aria_activate` files that were out of the research scope. My recommendation (recipes as Canon content + plugin tools) sidesteps this and matches the shipped `sec` pattern, so it does not block.

## 5. Effort + phasing

- **Phase 0 — Spike / confirm (0.5-1 week).** Read the core loader + `aria_data/server.py` to confirm recipe-dispatch mechanics and `PLUGIN_REQUIRED_FUNCTION` semantics. Stand up a skeleton `procurement.py` with one trivial tool (`aria_procurement_verify_line_math`) and confirm load + telemetry wrap.
- **Phase 1 — MVP: 1-2 deterministic skills through a thin plugin (1-2 weeks).** Extract the shared `numeric_kernel.py` into the plugin (8 tools). Author 2 recipes end to end: **invoice-rate-card-auditor** (near-pure `verify_line_math`/`percentile_gate`) and **should-cost-builder** (the `quadrature_rollup` "HARD RULE no model arithmetic" spine, LLM around it). Ship through Canon Builder. This proves the whole path (plugin → recipe → deterministic execution + narrative) with the two skills whose determinism is strongest and whose grounding data is either self-contained or already in Fabric.
- **Phase 2 — Broaden the deterministic core (2-3 weeks).** Add the 6 skill-specific kernels (tier, chain, complexity, roster, comment, pro-forma XLSX) and author recipes for the remaining Option B skills (market-rate-benchmarking, timeline-builder, workflow-map, evaluation-engine, legal-negotiation-prep, executive-summary-package, comment-cleanup, pro-forma-builder). Add the Option A pure-recipe chat skills (procurement-help-desk et al.), preserving the injection guard.
- **Phase 3 — Hard skills, scoped honestly (open-ended, gated).** Attempt the Option C skills as `tool_orchestration` recipes with the deterministic tools they can reach, explicitly accepting reduced fidelity, and hold anything needing net-new systems (Ariba/ServiceNow/Aravo/CLM) or missing primitives (docx-XML, JSX dashboards, web-research funnels) until a decision on whether ARIA gains those primitives. Do not commit dates here.

Rough total to a genuinely useful state (Phases 0-2): ~5-7 weeks of one engineer plus per-recipe Canon Builder review. Phase 3 is a research/product decision, not an estimate.

## 6. Open questions for the owner

1. **Fidelity bar for hard skills.** Is a lower-fidelity ARIA rendering of supplier-landscape / lilly-contract-review acceptable, or must those stay in the native skills suite and be out of ARIA scope? (My recommendation: keep them native; expose only their deterministic sub-steps to ARIA.)
2. **Deliverable formats.** Do ARIA users need the DOCX/XLSX/JSX-dashboard bundles, or is markdown + cached tables + the pro-forma XLSX enough? The dashboards do not port.
3. **New systems.** Is there any appetite to connect Ariba/ServiceNow/Aravo/CLM to ARIA (read-only), or does the locked reflect-don't-enforce / not-SoR posture keep those permanently out, capping ARIA procurement at Fabric spend + kernel math + narrative?
4. **Ownership of divergence.** The kernels are vendored byte-identical across skills today. If ARIA hosts a plugin copy, who owns keeping the plugin in sync with `lilly-procurement-kernels` as the canonical source evolves (a versioning/provenance discipline, per MAINTENANCE.md)?
5. **Which 1-2 skills seed the MVP?** I recommend invoice-rate-card-auditor + should-cost-builder; confirm, or substitute pro-forma-builder if a tangible XLSX deliverable is the more persuasive demo.
6. **Recipe-dispatch confirmation.** Approve a short Phase 0 spike to read the core loader before committing to recipes-as-content vs a generic `run_recipe` tool — the one contract detail the current research could not close.
7. **Trust tier + governance.** Ship `procurement` as `optional` + `beta` initially? And confirm every tool stays `readOnlyHint: True` (no PO/RFx writes), consistent with the Theo lock.
