## rfp-engine-1c344a

**Q1 In-Model Arithmetic.** No vendored `numeric_kernel.py` exists in this skill's own directory (only `rfp-response-analysis-1c344a`, `evaluation-engine-1c344a`, `sole-source-challenge-1c344a` vendor it). Weight math is instead governed by a prose self-check: SKILL.md:384 "**Evaluation-weight sanity check** ... within each category, the `Evaluation_Weight` values must sum to 100% ... If any category does not sum to 100%, or weights were not user-provided, label them 'DRAFT - confirm with evaluation team'." This is a MODEL-performed sum-and-compare, not a Python call. It is low-stakes (equal-weight defaults, draft labeling on failure per Rule 2, SKILL.md:160) but is still in-model arithmetic that could silently drift on a large requirements matrix since nothing enforces it mechanically.

**Q2 Deliverable vs Code.** Outputs table at SKILL.md:403-417: `message_compose` email drafts (hand-assembled per vendor, no builder), `[RFP|RFI]_Instructions.docx` (built by `assets/lilly_rfx_template.js`, a real Node.js docx-library builder confirmed in the file, e.g. `Document, Packer, Paragraph` from the `docx` package, lilly_rfx_template.js:34), `requirements_matrix.xlsx` / `pricing_template.xlsx` / `stakeholder_roster.csv` / `*.csv` schedules (no builder script present in `assets/`, so these are model-hand-assembled against the schemas in `references/artifact-schemas.md`), `demo_evaluation_guide.docx` (also hand-assembled, no builder), `case_handoff.json` (hand-assembled against `references/case-handoff-schema.md`). Only the Instructions doc has a real code builder; every other structured artifact (XLSX with "5-tier response scale and data validation," per SKILL.md:288) is asserted in prose with no code to guarantee the Excel data-validation or conditional formatting actually gets applied. On the JS-vs-Python question: a JS/Node runtime is defensible here specifically because the `docx` npm package is a mature, actively maintained DOCX-authoring library with strong support for headers/footers/TOC/complex tables (visible in the import list, lilly_rfx_template.js:34-37) that has no equivalent-quality Python analog in this suite's stack (`python-docx` is comparatively limited for this kind of magazine-quality branded template with badges/callouts). It is the one justified exception in the group; it should not be read as inconsistency so long as it stays isolated (it is: nothing else in the family uses JS).

**Q3 Runtime Cost.** SKILL.md is 11,243 words, the shortest of the five - runtime cost is low. The one loop that scales is per-vendor invitation emails (SKILL.md:426, "Produce one `message_compose` call per vendor"), fine at typical RFP scale (single digits to low tens of suppliers). The Stakeholder Requirements Synthesizer (SKILL.md:525-558) reprocesses every source document/transcript per requirement candidate in a single pass, not repeatedly, so no quadratic blowup found.

**Q4 Slice Contract.** ABSENT. No "output slice" or hub-dashboard contribution language anywhere in SKILL.md. An `rfx-hub` skill does not exist in the repo (confirmed by directory listing and grep). To feed a future rfx-hub, rfp-engine would need to expose: package status (Draft/Issued), artifact completeness (Step 1.1 selections), requirement count/category breakdown, and supplier invitation status - none of which is currently packaged as a bounded slice; it would have to be extracted from `case_handoff.json`.

**Q5 Routing.** `references/case-handoff-schema.md` is a genuinely good contract: versioned (`schema_version`), typed fields, an explicit validation-rules table (case-handoff-schema.md:109-120, e.g. "proposals_due must be after qa_deadline"), and an explicit list of receiver actions (case-handoff-schema.md:124-131). Cross-checked against `procurement-launcher-1c344a/references/routing-and-chains.md:88-90`, the documented chain (rfp-engine -> rfp-case-manager -> rfp-response-analysis -> evaluation-engine) matches what's in SKILL.md's own Skill Chain Position table (SKILL.md:483-487). The other four skills in this family all have equivalent inlined/companion handoff schemas: rfp-response-analysis emits `evaluation_engine_handoff.json` (schema inlined at SKILL.md:1973 with its own validation table), evaluation-engine's Upstream Handoff reference validates that inbound payload (SKILL.md:1167-1251), and sole-source-challenge emits `sole_source_justification_handoff.json` (SKILL.md:314). rfp-case-manager mirrors rfp-engine's schema rather than defining a new outbound one (it is a state-owner, not a pipeline producer). So the family's routing discipline is consistent, not just a one-off for rfp-engine.

**Q6 Best Version.** Build a real XLSX generator (Python, `openpyxl`) for `requirements_matrix.xlsx` and `pricing_template.xlsx` analogous to `lilly_rfx_template.js` for the DOCX. Today the 5-tier scale, data validation dropdowns, and conditional formatting claimed at SKILL.md:288 are produced by model-authored spreadsheet content with no code enforcing structure, which is the single highest-risk gap versus the DOCX path that already has a real builder.

## rfp-case-manager-1c344a

**Q1 In-Model Arithmetic.** This skill deliberately does NOT compute anything numeric - it is explicitly out of scope. SKILL.md:699 (Case File Schema `financials` block): "This skill does not price or score responses (see Boundaries) - populate only from a case_handoff.json flag, a value the user provides directly, or another skill's output the user pastes in. Never estimate a TCO or infer an award basis internally." The Case Status Visual's Preliminary TCO tile (SKILL.md:1232-1236) renders `CASE.financials.tco_confidence` as-is or shows a NEEDS_INPUT banner; it never derives a number. There is no `numeric_kernel.py` vendored here and none is needed given the boundary design. This is the correct answer to Q1 for this skill: no arithmetic, by design, and the design is honored consistently (Boundaries section, SKILL.md:143-150).

**Q2 Deliverable vs Code.** Every output in this skill is either JSON state (`_case_file.json`), Markdown (`timeline_{case_id}.md`, `meeting_drafts_*.md`, `case_summary.md`), CSV (`meeting_log.csv`), or an optional DOCX/JSX status snapshot - all hand-assembled by the model from schema, with no Python/JS builder file anywhere in this skill's directory (`ls` shows only SKILL.md, no assets/references folders; everything is inlined text). This is defensible for JSON/Markdown but the "Case Status Visual" (a JSX-rendered artifact with an 8-phase stepper, KPI tiles, and a deadline pill, SKILL.md:919-940) is exactly the kind of structured, repeatedly-rendered component that the suite's own `dashboard-components.md` house style pattern (referenced by other skills) argues should be a shared, code-driven component rather than freehand JSX authored per run.

**Q3 Runtime Cost.** SKILL.md is 15,373 words. The Status/Ingest/Refresh workflows each search up to four M365 surfaces (Outlook, Teams chat, calendar, SharePoint - SKILL.md:474-479) per invocation, but this is well-bounded: it uses `last_refresh` as an incremental lower bound (SKILL.md:377, "use the case file's last_refresh timestamp as the lower bound... state which bound you used") rather than rescanning the whole case history every time, which is good design. No identified per-supplier or per-requirement loop that scales badly; this is the best-controlled runtime story of the five skills, specifically because it defers all heavy analysis (scoring, requirement matching) to other skills per its explicit Boundaries.

**Q4 Slice Contract.** ABSENT in the "output slice for a hub dashboard" sense, but this skill already has the closest thing to one: the Case Status Visual (SKILL.md:919 "Reference: Case Status Visual") is a bounded, deterministic, single-case rendering built entirely from case-file fields (SKILL.md:394, "built entirely from fields already on the case file... Never fabricate a TCO, award basis, or Q&A count"). It is scoped to a single case and explicitly never aggregates across cases (SKILL.md:394), which is exactly the kind of bounded contract an rfx-hub would want to reuse or extend to multi-case rollups.

**Q5 Routing.** The inbound schema (`case_handoff.json` from rfp-engine) is mirrored, not re-derived: SKILL.md:723 explicitly notes it is a "Mirror of the rfp-engine case-handoff-schema reference." It also correctly flags that rfp-engine's own copy is stale (SKILL.md:723, "rfp-engine's source copy still describes legacy provisioning actions on receipt; under the v2.0 'no provisioning spec' decision, rfp-case-manager does NOT create SharePoint folders or Teams sites"). This is a real drift between the two schema copies (rfp-engine's case-handoff-schema.md:124-131 still lists "recommend where artifacts belong" and folder-mapping actions consistent with older behavior) that rfp-case-manager has patched over in its own copy but rfp-engine's copy was never corrected to match. This is a documentation-sync bug worth fixing.

**Q6 Best Version.** Reconcile the case-handoff-schema.md duplication: make rfp-engine's copy either a pointer to a single canonical file, or update rfp-engine's copy to drop the stale provisioning-actions language noted as inconsistent in rfp-case-manager's own SKILL.md:723. Two independently-maintained copies of the same schema is exactly the drift-prone pattern the numeric_kernel vendoring approach was designed to avoid for arithmetic; the same discipline should apply to shared JSON schemas.

## rfp-response-analysis-1c344a

**Q1 In-Model Arithmetic.** This skill vendors `numeric_kernel.py` and its generator (`rfp_analysis_report_generator.py`) genuinely calls it: rfp_analysis_report_generator.py:217-219 imports `weighted_score`, `WeightSumError`, `InvalidInputError` from `numeric_kernel`, and line 1374 calls `kernel_weighted_score(scores_map, renorm_weights)` inside `compute_ground_truth`-equivalent logic, refusing (not guessing) when weights don't foot (line 1378). SKILL.md itself echoes this at line 1976-1977: "The weighted-sum arithmetic behind this matrix is computed by calling weighted_score() in the vendored numeric_kernel.py." However, the Phase 4 Bid Leveling normalization (the price-per-scenario recomputation) is NOT kernel-backed - it is prose-instructed model arithmetic: SKILL.md:328, "recompute each supplier's reported price onto the common comparison basis... Show the normalization arithmetic (reported figure, the unit conversion applied, the resulting normalized figure) so the evaluation team can audit it." The kernel has no bid-leveling/scenario-normalization function (only `to_hourly`, `convert_currency`, `npv`, `escalate`, `quadrature_rollup`, `weighted_score` - confirmed by reading numeric_kernel.py in full), so this entire gating computation, which the Grand Total and ranking depend on (SKILL.md:571, "Bid Leveling gates ranking"), is done by the model, not code. This is the single biggest correctness risk in this skill: the weighted-average step is kernel-verified, but the upstream input to that average (the normalized price) is not.

**Q2 Deliverable vs Code.** Primary deliverable `analysis_summary.docx` (30-40 pages, SKILL.md:430) is built by `rfp_analysis_report_generator.py` (2,935 lines), which does real DOCX assembly via `python-docx` (imports confirmed at line 244-249) and genuinely computes ground truth via the kernel before rendering (line 1340-1382). This is the most code-complete generator of the group. The interactive dashboard is JSX described inline in SKILL.md (around line 945-1400) rather than a separate file - hand-assembled per the suite's dashboard convention, consistent with the other skills. CSV outputs (`clarification_questions.csv`, `bid_leveling_worksheet.csv`, `bid_leveling_register.csv`) are schema-documented in `references/bid-leveling.md` but have no dedicated Python writer distinct from the DOCX generator; they appear to be produced by the model against the documented schema.

**Q3 Runtime Cost.** SKILL.md is ~29,273 words (confirmed by `wc -w`), by far the largest in the suite. The specific slow mechanism is not just size: it is the mandated 3-pass DOCX assembly (SKILL.md:554-555, "Pass 2: Open the saved document and append... Pass 3: Confirm the GATE CHECK... then open the saved document and append all cross-cutting sections") combined with a hard sequencing dependency - Bid Leveling (Phase 4) must fully complete for every pricing supplier before Sections 6-13 (cross-vendor comparison, weighted scoring, pricing analysis, recommendation) can even start (SKILL.md:555, 571, 637). For an RFP with many suppliers, this is a per-supplier-times-per-scenario normalization pass gating a second per-supplier-times-per-criterion scoring pass, done serially across 3 document-reopen cycles, each requiring the model to re-read its own prior output to append correctly. This is the concrete slow mechanism: repeated whole-document re-opens plus a strict two-stage supplier x scenario, then supplier x criterion, dependency chain, not merely a long SKILL.md.

**Q4 Slice Contract.** ABSENT - no "output slice" language found. To feed a future rfx-hub, this skill would need to expose: per-supplier requirement-coverage %, Bid Leveling gate status (complete/pending per supplier), and the AI-proposed scoring skeleton it already hands off in `evaluation_engine_handoff.json` - which is largely there already, just not framed as a hub slice.

**Q5 Routing.** Its downstream handoff, `evaluation_engine_handoff.json` (schema inlined at SKILL.md:1973-2097), is comparable in rigor to rfp-engine's case-handoff-schema.md: versioned, has an explicit consumer validation table (SKILL.md:2073-2089), and mandates citation-provenance preservation ("All source_document and source_location values from this handoff must be preserved in evaluation-engine's downstream outputs"). This is a well-built, symmetric pair with evaluation-engine's own "Upstream Handoff" consumption logic (see evaluation-engine Q5 below) - the two skills were clearly co-designed.

**Q6 Best Version.** Extend `numeric_kernel.py` (or add a sibling function in the same vendored module) to implement Bid Leveling's price normalization formula as code, and have `rfp_analysis_report_generator.py` call it the same way it already calls `weighted_score()`. This closes the one arithmetic gap in an otherwise kernel-disciplined skill, and it is the step that most directly protects the ranking, since Section 13 and the Award Recommendation are explicitly gated on Bid Leveling's output (SKILL.md:571).

## evaluation-engine-1c344a

**Q1 In-Model Arithmetic.** Correctly kernel-backed. `evaluation_report_generator.py:171` imports `weighted_score as kernel_weighted_score`, and line 696 calls `kernel_weighted_score(scores, weights)` per supplier inside `compute_ground_truth`, explicitly refusing to hand-compute (line 676-677, "HARD RULE, kernel-computed weighted score... Import error" raised rather than falling back to manual math). SKILL.md itself documents this as a hard rule with a validation table (referenced at numeric_kernel.py's own docstring, "evaluation-engine-1c344a/SKILL.md, Score Validation Checks: Effective weight sum... must sum to 1.0 +/- 0.001"). SKILL.md:665 in the dashboard JSX also states "the blend math itself is computed client-side by the dashboard renderer via weighted_score(), not precomputed into the JSON" - i.e. even the interactive award-scenario blend slider stays kernel-driven rather than becoming ad hoc JSX arithmetic. This is the cleanest Q1 answer of the five real-scoring skills.

**Q2 Deliverable vs Code.** `evaluation_report.docx` (or equivalent) is built by `evaluation_report_generator.py` (1,862 lines), which genuinely renders the ground-truth object computed via the kernel (lines 1048-1132 show DOCX paragraph construction reading `gt.grand_total[sid]`, `gt.weighted_contribution`). `ai_scoring.csv` and the dashboard JSX are schema-documented but not separately code-generated. This is the second-most code-complete generator after rfp-response-analysis's, and the one place where the code path is demonstrably airtight for the number that matters most (the Grand Total / award recommendation).

**Q3 Runtime Cost.** SKILL.md is 14,822 words. The workflow runs Phases 1 through 6+ with a per-supplier, per-criterion scoring loop; because the kernel call is O(criteria) per supplier and criteria counts are typically small (single digits to low tens), this scales fine. The main cost driver is the AI-scoring skeleton import/verification step when a handoff is present (SKILL.md:195-208), which is a verification pass over already-extracted data rather than re-extraction - a well-designed cost reduction versus re-deriving from raw documents.

**Q4 Slice Contract.** ABSENT - no explicit "output slice" text. This skill is arguably the best-positioned of the five to define one, since its `scoring_grid` array (SKILL.md:936, one entry per supplier: `ai_score`, `stakeholder_score`, `landscape_fit_score`, `coverage_pct`, `grand_total`, `award_tier`, `gate_detail`) is already a clean, bounded, per-supplier record that a hub could consume directly with minimal reshaping.

**Q5 Routing.** Consumes `evaluation_engine_handoff.json` via its own "Upstream Handoff" reference (SKILL.md:1167-1251), with validation rules (schema_version check, generated_by check) mirroring rfp-response-analysis's producer-side rules. Downstream, SKILL.md:585's Skill Chain Position table names only "contract negotiation chain" generically rather than a named next skill or a JSON handoff schema - this is the one weak link in the family's routing: every other skill in this group hands off a named, schema-defined JSON file to a named next skill, but evaluation-engine's outbound side is not similarly formalized in-file (routing-and-chains.md:75 also just says `"contract negotiation chain"` with no schema pointer).

**Q6 Best Version.** Formalize an outbound `evaluation_engine_award_handoff.json` (built from the already-well-shaped `scoring_grid` array) with the same schema-version/validation-table discipline as its own inbound Upstream Handoff reference, naming commercial-negotiation-prep or lilly-contract-review as the explicit consumer. This closes evaluation-engine's asymmetry: excellent inbound handoff discipline, no matching outbound one.

## sole-source-challenge-1c344a

**Q1 In-Model Arithmetic.** Best-documented kernel discipline in the group. SKILL.md:98 states as a hard rule: "**G11 (Kernel-Backed Computation):** This skill vendors numeric_kernel.py. The Sole-Source Defensibility Score is computed ONLY by calling weighted_score() in that kernel, never by model arithmetic." SKILL.md:268-280 shows the literal call pattern (`from numeric_kernel import weighted_score`, then `defensibility_score = weighted_score(scores, weights)  # example: 3.475`), and its pre-delivery checklist (SKILL.md:354) requires "The Defensibility Score is the kernel's weighted_score() return value, shown with the full calc table; weighted_contribution values sum to it." This is the only one of the five SKILL.md files that names its kernel rule with a G-number in the shared G1-G10 guardrail numbering scheme (extending it to G11), making the dependency impossible to miss on a read-through.

**Q2 Deliverable vs Code.** `sole_source_generator.py` (2,487 lines) "mechanically renders Deliverable #1... from a single validated sole-source register... into EITHER of two output formats [DOCX or PPTX], both driven by the identical data model, never freehand-authored" (SKILL.md:333). This is the cleanest deliverable-to-code mapping in the family: one data model, one generator, two format targets, with the Defensibility Score itself flowing from the kernel call rather than being re-typed into the document. `challenge_scorecard.csv`, `alternatives_register.csv`, and `sole_source_justification_handoff.json` are the other outputs (SKILL.md:314) - these are schema-documented but not shown to have a dedicated writer separate from the main generator; given the small, single-supplier scope of this skill, that risk is much lower than in the multi-supplier skills.

**Q3 Runtime Cost.** SKILL.md is 7,116 words, the smallest in the family. Scope is a single proposed/incumbent supplier scored across seven fixed dimensions (not per-supplier-times-N), so there is no scaling loop of concern. This is the most efficient skill in the group by a wide margin, structurally as well as textually.

**Q4 Slice Contract.** ABSENT - no "output slice" language. Its natural hub contribution would be a single record: verdict (Defensible/Weak/etc.), Defensibility Score, and the SME-routing/evidence-count summary already described in its Phase 4 tab (SKILL.md:369).

**Q5 Routing.** `sole_source_justification_handoff.json` (SKILL.md:314) is consumed by three named downstream skills (process-navigator, commercial-negotiation-prep, executive-summary-package - SKILL.md:396 and routing-and-chains.md:93), each with a stated purpose ("the evidence its New-Supplier Governance widget checks as Filed"; "on a DEFENSIBLE verdict, the price-validation band becomes the negotiation anchor"). This is a fan-out handoff (one producer, three named consumers) rather than the linear producer-to-single-consumer pattern used by rfp-engine/rfp-response-analysis/evaluation-engine, and it is documented with equal specificity. Cross-checked against routing-and-chains.md:93, the fan-out is confirmed consistent between the skill's own text and the suite-wide routing map.

**Q6 Best Version.** Given this skill is already the cleanest (small, kernel-backed, single generator), the highest-value improvement is upstream rather than internal: wire `numeric_kernel.py`'s `quadrature_rollup` (already vendored but unused here) into the Price Validation Substitute evidence dimension when should-cost-builder or market-rate-benchmarking data is available, so the price-band evidence gets the same kernel-computed confidence range treatment those source skills use natively, instead of being carried forward as a flat point estimate.

## Cross-Cutting Notes

- **Kernel adoption is inconsistent within the family.** evaluation-engine and sole-source-challenge call `weighted_score()` correctly and say so explicitly (sole-source-challenge even added a G11 rule for it). rfp-response-analysis calls it correctly for the final weighted average but NOT for the upstream Bid Leveling price normalization that gates that average - a real gap given Bid Leveling explicitly gates the ranking (SKILL.md:571). rfp-engine has no kernel at all and does a weight-sum check in prose (SKILL.md:384). rfp-case-manager correctly has no kernel because it correctly has no arithmetic.
- **Handoff schemas are a genuine family strength**, not a one-off for rfp-engine: all four scoring/document-producing skills (rfp-engine, rfp-response-analysis, evaluation-engine, sole-source-challenge) have versioned, validated JSON handoff schemas with named consumers, cross-checked against `procurement-launcher-1c344a/references/routing-and-chains.md`. The one weak spot is evaluation-engine's outbound side ("contract negotiation chain" named generically, no schema) and a stale duplicate of case-handoff-schema.md living in rfp-engine that rfp-case-manager's own text says it no longer follows.
- **No skill in this family defines an "output slice" for a hub dashboard** - the concept exists only in suite-level planning docs (PROGRAM-MASTER-PLAN.md, MASTER-REMAINING-WORK.md), not inside any of these five SKILL.md files, and `rfx-hub` does not exist as a skill directory.
