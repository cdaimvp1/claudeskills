## lilly-contract-review-1c344a

**Q1 In-model arithmetic.** Mostly delegated, but the Protection Score itself is not. `SKILL.md:1000` states line-item math and escalation MUST be computed by `verify_line_math()` / `escalate()` in `numeric_kernel.py`, and this is followed (not re-derived in prose). However the Protection Score (`references/risk-scoring.md`) is a model-judgment sum: "Select the deduction range... within the range, use judgment... Sum all deductions. Subtract from 100" (risk-scoring.md lines ~20-30). This is additive arithmetic (subtraction from 100, summing a table of deductions) done by the model, not by `numeric_kernel.py`, even though the kernel is vendored in this same skill and already implements `weighted_score()`. The worked example even shows a literal footing check ("Total deductions: -36... Score: 64") that a Python function should own.

**Q2 Deliverable vs code.** Emits: redlined .docx (hand-assembled via docx skill/tracked changes, no builder script), dashboard .jsx (JSX authored directly by the model per `references/dashboard-canonical.md` and `examples/contract_review_canonical_dashboard.jsx`, no build script converts data->JSX), vendor response draft (prose), findings ledger .json (SKILL.md:273, generated from PASS_4_PREP data object, not separately authored, but still hand-emitted JSON, no serializer script), governing-document stack map .docx + manifest .json (Step 0.5). No builder file exists anywhere in the skill folder besides `numeric_kernel.py`; every artifact is model-authored text/JSX/JSON.

**Q3 Runtime cost.** SKILL.md is 23,446 words (`wc -w`), the largest of the five. Mechanism: a mandatory four-pass workflow (Pass 1 Structural Scan, Pass 2 Substantive Review section-by-section against the playbook, Pass 3 Vendor Tactics, Pass 4 QA "re-read all findings against the governing document landscape", SKILL.md:648) run per document, plus Layer 1 governing-document discovery reading the MSA/exhibits/amendments in full before the WO/SOW itself. "Walk through the contract section by section... produce a finding for every deviation" (SKILL.md:894) is a per-clause loop. Full review mode additionally builds a 3-panel/7-sub-tab dashboard requiring the same depth as the DOCX, effectively doubling authored content per run.

**Q4 Slice contract.** ABSENT. No named JSON block this skill "owns" for a hub dashboard is defined; the findings ledger JSON (SKILL.md:273) is a downstream-ingestion sidecar for other skills (negotiation-playbook-learning, theos-field-guide), not a hub-dashboard slice contract.

**Q5 Routing.** Downstream: negotiation-playbook-learning, theos-field-guide (SKILL.md:273); legal-negotiation-prep and commercial-negotiation-prep absorbed as native panels (SKILL.md description). Matches `routing-and-chains.md:80`: "lilly-contract-review | negotiation-playbook-learning (outcome data...), market-rate-benchmarking | negotiation-playbook-learning (outcomes recorded after negotiation); absorbs legal-negotiation-prep and commercial-negotiation-prep panels." No contradiction found.

**Q6 Best version.** Move the Protection Score calculation (sum-of-deductions-from-100, with a bounded per-severity range) into `numeric_kernel.py` as a new function, e.g. `protection_score(deductions: list[tuple[severity, coverage_status, deduction]]) -> int`, with the anti-drift calibration check (30-point ceiling for zero-Hard-Stop/10+-Covered documents) enforced as a refusal/warning inside the function rather than as prose the model must remember to self-check.

## legal-negotiation-prep-1c344a

**Q1 In-model arithmetic.** No numeric arithmetic is asked of the model; this skill's only "kernel" decision is non-numeric tier classification. It vendors `tier_kernel.py` (its own file, not `numeric_kernel.py`) and Phase 2 explicitly states "do not hand-classify the tier. Call `assign_tier(term_attrs)`... never by model prose reasoning against the table" (SKILL.md:302). The kernel is called correctly, is binding for playbook/MSA-derived tiers, and abstains to `NEEDS_LLM` for genuinely un-derivable commercial terms rather than fabricating a rule. This is the cleanest kernel-wiring of the five skills.

**Q2 Deliverable vs code.** Emits one artifact: `[Supplier]_Negotiation_Briefing_v[N].docx` (SKILL.md:407), built via the `docx` skill directly from an inlined design spec (color palette, typography, layout) with no separate builder script; it is hand-assembled per-run from the design spec's field templates, not generated by code. An optional inline JSON session/position-map snippet is also hand-composed.

**Q3 Runtime cost.** SKILL.md is 15,159 words. Mechanism: Phase 1B runs an explicit two-pass "Source Collection" for >$1M negotiations (Pass 1 collect, Pass 2 re-read with WO/SOW scope in mind, SKILL.md:230-241), and Phase 2 calls `assign_tier()` once per playbook term ("For every playbook section relevant to this contract type" -- SKILL.md:293), which is a per-term loop bounded by playbook size, not document length, so it scales more gently than lilly-contract-review's per-clause loop.

**Q4 Slice contract.** ABSENT. No named owned JSON block for a hub dashboard; only the DOCX briefing plus an in-document Position Map & MSA Coverage panel are specified.

**Q5 Routing.** Upstream: lilly-contract-review (playbook, SME matrix, pharma requirements), negotiation-playbook-learning (supplier outcomes) -- SKILL.md:435-439. Downstream: lilly-contract-review and negotiation-simulator (optional rehearsal hand-off) -- SKILL.md:441-445. Matches `routing-and-chains.md:78` exactly: "legal-negotiation-prep | lilly-contract-review..., negotiation-playbook-learning... | lilly-contract-review..., negotiation-simulator (tiered positions and fallback sequencing for rehearsal, optional)." No contradiction.

**Q6 Best version.** The `is_playbook_position` / `msa_conflict` gate inputs the kernel requires (SKILL.md:304) are themselves currently populated by unstructured model judgment during Phase 1A/Source A reads. Building a lightweight extraction helper (even a simple keyword/definition matcher against `playbook.md` section headers) to pre-populate these two boolean gate inputs would reduce the chance of the LLM mis-classifying a term at the one input boundary the kernel cannot itself verify.

## comment-cleanup-1c344a

**Q1 In-model arithmetic.** None. This skill has no numeric computation; its vendored kernel (`audience_kernel.py`) is a non-numeric decision kernel (keep/strip/redact/review), and the Kernel Wiring section (SKILL.md:167-186) requires calling `mode_action()`/`strip_action()` for every comment/redline rather than hand-deciding. Verified by reading the full kernel: it is a pure lookup-table/decision-tree with typed REVIEW/NEEDS-style abstention for anything SKILL.md doesn't state a rule for (e.g. `(SUPPLIER_FACING, LEADERSHIP_SUMMARY)` cell deliberately routes to REVIEW rather than guessing, kernel lines ~393-406).

**Q2 Deliverable vs code.** Emits: cleaned .docx (via `docx` skill or in-document edit, hand-assembled), a hygiene report (chat/inline text), and for Mode B a "change summary." No dedicated builder script exists beyond the decision kernel; the kernel decides actions, the model executes the edits inline via the docx tool.

**Q3 Runtime cost.** SKILL.md is 8,130 words, the smallest of the five. Mechanism: Step 1 requires per-comment classification and Step 2 runs multiple hygiene scans (consolidation, removal, shortening, strategy-leak, audience) over every comment; Mode B additionally requires calling `mode_action()` once per comment AND once per redline (tracked change) in the whole document, which is the same order of magnitude as document size for a heavily-redlined contract, though comment counts are typically much smaller than clause counts.

**Q4 Slice contract.** ABSENT. No hub-dashboard JSON slice; deliverable is a hygiene report plus an edited DOCX, described as "Word-native" (SKILL.md:508).

**Q5 Routing.** SKILL.md states only "Integrated with lilly-contract-review: The contract review skill's Step 5D calls this workflow inline" (SKILL.md:458). Matches `routing-and-chains.md:72`: "comment-cleanup | lilly-contract-review (called inline from Step 5D...) | none stated separately (it is the terminus of that inline call)." No contradiction; both agree this skill has no further downstream.

**Q6 Best version.** The skill's own "Maintainer note" (SKILL.md:452) already flags the highest-value structural improvement: extracting "Finalize for Signature" (Mode B, which touches operative contract body text via tracked-change acceptance) into its own skill, since it is a materially higher-risk surface hidden inside a lower-stakes comment-hygiene skill name, hurting discoverability and mixing risk profiles under one trigger set.

Rule 6 and Rule 8 (SKILL.md:364-381) require `verify_line_math()` for payment-milestone reconciliation and `weighted_score()` for the Scope Definition Score composite, with an explicit findings-severity coupling ceiling (BLOCKING caps a dimension at 0.9, HIGH at 3.4, MEDIUM at 4.4) enforced as a validity condition (G9) rather than left to model judgment. The Kernel Wiring table (SKILL.md:392-408) also assigns `to_hourly()` for rate-unit normalization and `escalate()` for multi-year rate escalation checks, covering every arithmetic operation the skill performs; no formula is re-derived in prose.

**Q2 Deliverable vs code.** Emits up to seven artifacts (SKILL.md:554-564): Scope Diagnostic Report (.docx, hand-assembled Magazine Report style, no builder script), `scope_diagnostic_dashboard.jsx` (hand-authored JSX against `dashboard-canonical.md`, no build script), `Rewritten_SOW.docx` (hand-assembled), `rate_card_and_payment_schedule.xlsx` (described as having "formulas live so the user can adjust inputs," i.e. real spreadsheet formulas, the closest thing to a builder among the five skills but still authored per-run, not from a template script), `raci_matrix.csv`, `change_control_log_template.xlsx`, `scope_findings.json` (generated from PASS_4_REBUILD, not separately authored). No dedicated Python/JS builder file exists besides `numeric_kernel.py`.

**Q3 Runtime cost.** SKILL.md is 7,552 words, the second-smallest. This is a fixed four-pass overhead independent of document length, more contained than lilly-contract-review's open-ended per-clause finding generation.

**Q4 Slice contract.** ABSENT as a hub-dashboard slice, but this skill defines the most complete standalone machine-readable sidecar of the five: `scope_findings.json` with an explicit schema (SKILL.md:564) including a header block `{engagement_type, total_value, term, scope_definition_score, dimension_scores{...}, payment_reconciles, as_of_date}`. Matches `routing-and-chains.md:91` verbatim. No contradiction.

## negotiation-simulator-1c344a

**Q1 In-model arithmetic.** This is the clearest violation in the group. The skill has no vendored kernel at all (only `examples/negotiation_simulator_position_playbook.jsx` in its directory; no `numeric_kernel.py`, no local kernel), yet the Structured Debrief section instructs the model to compute: (1) a reciprocity ratio "`M / N` rounded to one decimal" with multiple branch cases (SKILL.md ~464-469), and (2) anchor effectiveness "`capture% = (W - Z) / (Y - Z) * 100`" with edge-case handling for >100%, zero-range, and wrong-direction results (SKILL.md ~471-475). Both are exactly the kind of small, deterministic, edge-case-heavy arithmetic `numeric_kernel.py` exists to own (it already has `weighted_score` and generic ratio-shaped guards), but this skill re-derives the formulas and their degenerate-case handling entirely in prose rather than calling or vendoring the kernel.

**Q2 Deliverable vs code.** Native deliverable is the live chat roleplay itself (no file). Optional artifacts: a saved debrief (inline text, optionally a file), an opt-in session-outcome JSON (hand-composed inline per a documented schema, SKILL.md ~489-506), and an optional Position Playbook .jsx (built by cloning `examples/negotiation_simulator_position_playbook.jsx`, SKILL.md:434, "clone its structure, swap the data" -- effectively a manual template-clone, not a code generator). Every artifact is model-authored text/JSON/JSX; there is no builder script anywhere in this skill folder.

**Q3 Runtime cost.** SKILL.md is 12,444 words. The dominant cost driver is not document length but session length: Drill mode is explicitly "open-ended length (5 to 20+ exchanges typical; not capped to 3-5)" (SKILL.md ~320) with a [Supplier]/[User]/[Coach] triple every exchange, and Internal Executive Challenge runs up to 10 stress-test dimensions x up to 7 reviewer personas with per-response coaching, i.e. a combinatorial persona x dimension loop that can run long. Unlike the document-driven skills, this cost is turn-count-driven and not bounded by any single input size.

**Q4 Slice contract.** ABSENT. Chat-native low-artifact skill by design ("this skill still renders no multi-tab dashboard," SKILL.md:432); no hub-dashboard JSON block is owned.

**Q5 Routing.** SKILL.md Integration section (SKILL.md:593-595): consumes lilly-contract-review, negotiation-playbook-learning, legal-negotiation-prep/commercial-negotiation-prep, supplier-risk framework; feeds the real negotiation and negotiation-playbook-learning (opt-in outcome record). Matches `routing-and-chains.md:84` exactly: "negotiation-simulator | lilly-contract-review..., negotiation-playbook-learning..., legal/commercial-negotiation-prep... | the real negotiation; negotiation-playbook-learning..." No contradiction. Also cross-verified against legal-negotiation-prep's own downstream line (routing-and-chains.md:78) naming negotiation-simulator as an optional downstream -- consistent both directions.

**Q6 Best version.** Vendor a small local kernel (or import `numeric_kernel.py`'s pattern) implementing `reciprocity_ratio(given, received)` and `anchor_capture_pct(open, final, target)` as pure functions with the degenerate cases (zero-zero, one-sided, beyond-target, wrong-direction, zero-range) as typed return values, exactly mirroring what `numeric_kernel.py` already does for other skills' ratio/percentage math. This is directly buildable: the prose in SKILL.md already specifies the exact formulas and every edge case, so the kernel could be written by mechanically transcribing the existing spec, the same process used to build `numeric_kernel.py` from the other skills' prose.
