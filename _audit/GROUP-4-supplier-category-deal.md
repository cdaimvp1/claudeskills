It would need a new "Output slice contract" section (modeled on deal-tab-1c344a's, see below) only if it were ever composed into a larger hub; today it hands off via `landscape_handoff.json` to rfp-engine (SKILL.md:320-322), which is a handoff contract, not a slice-ownership table.

**Q6 (best version).** Move the Weighted Scoring Matrix's "multiply by weight, sum" instruction (SKILL.md:341-362) into a small vendored `numeric_kernel.py` function (a `weighted_score()` call, mirroring deal-room's own kernel usage) so the DOCX table and the dashboard headline can never independently drift, and so G11-style kernel-backed computation applies here too. Concretely: add `supplier-landscape-1c344a/numeric_kernel.py` with a `weighted_score(scores, weights)` function, and change SKILL.md:358 to instruct calling it rather than "multiply... sum" in prose.

## deal-room-1c344a

**Q1 (in-model arithmetic).** This skill is the strictest of the five on this point. G11 (SKILL.md:83) states: "every computation the kernel covers... is produced by calling the kernel, never by model arithmetic or a re-derived estimate. If the kernel is missing or errors on the given input, STOP and report the failure." Phase 3 (SKILL.md:329-338) names exactly which function applies to which case (`escalate()`, `weighted_score()`, `npv()`) and explicitly carves out the one case that is deliberately plain arithmetic (simple per-unit single-year deltas), requiring that case to be labeled as such rather than implied to be kernel-verified. Confirmed: `deal-room-1c344a/numeric_kernel.py` exists and is referenced by name throughout Phase 3 and the inlined `deal-room-state-schema.md`.

**Q2 (deliverable vs code).** Deliverables per the Deliverables table (SKILL.md:444-453): `deal_room_state.json`, round-update chat text, the Deal Room Dashboard, the Next-Round Meeting Brief, draft counter/email, and close-out `negotiation_outcome.json` + `deal_close_summary.md`. The dashboard has a real builder confirmed on disk: `dashboard/build_deal_artifact.py` plus `dashboard/_parts/*.js` and `dashboard/_platform_build/`. SKILL.md:413 states the deterministic pattern explicitly: "you author the data object `dashboard/_parts/data.js`, then run `dashboard/build_deal_artifact.py`; the shipped, locked engine renders every tab." The state JSON, brief, and handoff files have no builder script; they are model-authored per run (expected, since they are structured text/JSON, not rendered UI).

**Q3 (runtime cost).** Per-round parsing (Phase 2) is bounded and cheap (one free-text account per round). The heaviest cost driver is not a loop but a persistence/consistency burden: the Numbers-reconcile assertion (inlined `deal-room-state-schema.md`) must be re-verified before every state write or dashboard render, checking priority-weight sums, per-round given/received totals, and package-linkage integrity across the whole `rounds[]` history, which grows unbounded across a long negotiation (append-only, Phase 2 Step 3). This is well-justified by the reflect-only/no-re-merge design, not wasteful, but it is the one place cost scales with negotiation length.

**Q4 (slice contract).** deal-room-1c344a is a hub that CONSUMES slices from other skills into `deal_room_state.json.hub_slices` (SKILL.md:620-626: `legal_protection`, `scope_performance`, `landscape`, each `null | object` with NEEDS_INPUT fallback) but does not itself define a slice contract for what it contributes to a still-larger hub; it is the hub, not a lens. This is a legitimate architectural difference from deal-tab (which is a static hub with lens-owned slices) rather than a gap, since deal-room's own SKILL.md:157-177 ("Deal SKILL HOME") already documents composition direction clearly.

**Q5.** Not applicable.

**Q6 (best version).** The `hub_slices` block is well-designed but its provenance/staleness discipline is not enforced by a re-check the way the numbers-reconcile assertion is. Concrete improvement: add a "Slice staleness assertion" to the inlined `deal-room-state-schema.md` requiring each populated `hub_slices.*` entry's `provenance` timestamp be checked against a skill-specific staleness window (e.g., contract-review slice re-verified if older than 30 days) before rendering the Terms & Review tab, with a stale slice rendering a distinct "STALE, refresh from {skill}" state rather than silently reusing old data.
