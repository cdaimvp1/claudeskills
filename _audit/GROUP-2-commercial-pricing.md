## commercial-negotiation-prep-1c344a

**Q1 In-model arithmetic:** Kernel calls are explicitly wired for three things: escalation/TCO (`SKILL.md:505` "must be produced by calling `escalate(base, rate, year, compounding)` from `numeric_kernel.py`, not by freehand or estimated arithmetic"), the percentile gate (`:961` "call `percentile_gate(n_points, min_points=5)`... Below Market (<=P50): [N] ([X]%)... Total Annual Exposure: $[amount]" has no kernel binding at all). This is the most numeric-narrative-heavy skill in the group and the least kernel-covered relative to its own complexity.

**Q2 Deliverable vs code:** Deliverables: `[Supplier]_Commercial_Briefing_v[N].docx` via the generic `docx` skill (`:609`), `rate_comparison.xlsx` and `counter_offer.xlsx` via the generic `xlsx` skill (`:612-613`), and an optional `[Supplier]_Negotiation_Dashboard.jsx` hand-assembled per G10 chunked-write discipline (`:619` "Phase 10... No skill-specific builder .py exists anywhere in this skill's directory (only `SKILL.md` and `numeric_kernel.py` on disk); every artifact is model-assembled at generation time, not code-built, aside from the three kernel calls noted in Q1.

**Q3 Runtime cost:** SKILL.md is 20,202 words, by far the longest in this group. Phase 1B mandates, for engagements with >5 rate lines, "3-5 independent data points per rate line" across "3 independent web searches per rate line" (`:250-256`), so a 20-rate-line rate card requires roughly 60 web searches before Phase 2 even starts; this is a genuine per-rate-line search loop, not just a large reference file. The 10 sequential phase gate-checks (`:291,317,369,410,459,507`, etc.) also force a strict multi-pass workflow with an intermediate artifact required at every gate, adding turn overhead proportional to rate-line count.

**Q4 Slice contract:** ABSENT. No "output slice," `commercialLines[]`/`scenarios[]`-style schema, or hub-dashboard ownership language appears anywhere in the file; the dashboard in Phase 10 is this skill's own standalone 4-tab artifact, not a slice feeding a shared hub.

**Q5 Routing:** Matches `routing-and-chains.md:73` exactly: predecessors rfp-engine/evaluation-engine, negotiation-playbook-learning, market-rate-benchmarking; successors legal-negotiation-prep, pro-forma-builder, should-cost-builder. SKILL.md's own "Integration Dependencies" section (`:660-670`) and BOUNDARY lines (`:11-14`) name the same three successors and predecessors. No contradiction found.

**Q6 Best version improvement:** Build a dedicated `commercial_negotiation_generator.py` (mirroring should-cost/market-rate/pro-forma's pattern) that takes the validated rate-line register plus the kernel outputs and computes the Pricing Position Summary percentages, Total Annual Exposure, Total Leverage Value, and Combined Target deterministically, then writes `rate_comparison.xlsx` and `counter_offer.xlsx` directly via `openpyxl` instead of routing through the generic `xlsx` skill. This is the one skill in the group with genuine multi-line percentage/rollup math (Pricing Position Summary bands) still fully unkernelled.

## invoice-rate-card-auditor-1c344a

**Q1 In-model arithmetic:** Strongly kernel-gated by a dedicated guardrail, G11 (`:100`): "All rate verification and escalation-cap arithmetic MUST be computed by calling the vendored `numeric_kernel.py`, never performed in prose or by model judgment." `verify_line_math()` is called "For every invoice line that bills `rate x hours/quantity = line total`" (`:191`) and escalation caps via `escalate()`. It also states a strict fail-closed rule (`:193`): "A figure produced without the kernel is invalid... the skill STOPS on that specific line... does NOT fall back to estimating the figure in prose." This is the strictest anti-fabrication wiring of the group, though it has no dedicated generator .py for its xlsx/docx outputs the way pro-forma-builder does.

**Q2 Deliverable vs code:** Deliverables: a 7-tab locked dashboard (Overview, Line-Level Exceptions, Rate & Escalation, Hours & Quantity, Duplicate & Unsupported, Category Rollup & Credits, Dispute Notice & Ledger), a DOCX audit report, a "portable JSON findings ledger," and a draft supplier dispute notice (`:156`). No skill-specific builder .py exists in this directory (only `SKILL.md` and `numeric_kernel.py`); the JSON ledger and DOCX are model-assembled from the per-line kernel outputs, not code-built, though every individual rate/math figure inside them traces to a kernel call.

**Q3 Runtime cost:** SKILL.md is 13,798 words. The workflow is an explicit 5-pass pipeline (PASS_1_EXTRACT through PASS_5_OUTPUT, `:199,203,227,251,280,311`) and, unlike the search-driven skills above, its scaling risk is a per-invoice-line loop over the model's own reasoning: "For every invoice line, resolve it against the other documents" (`:229`) and "For every line with a rate-card match... call `verify_line_math`... flag any `False` result" (`:256`), with G5 requiring "the complete findings data object (every line, every finding, every rollup)" be built before any rendering (`:94`). For an invoice population of hundreds or thousands of lines, this is a genuine per-line-item loop executed by the model turn-by-turn (each kernel call still requires the model to invoke it per line), not a batch/vectorized pass; there is no described mechanism to batch multiple lines into one kernel call or one code execution.

**Q4 Slice contract:** ABSENT. No hub-slice schema language found; explicitly "Reflect-only throughout... never writes back to AP, an ERP, or Ariba" (`:156`), a standalone audit tool.

**Q5 Routing:** Matches `routing-and-chains.md:77` exactly (no predecessors stated; successors commercial-negotiation-prep, market-rate-benchmarking, executive-summary-package). SKILL.md's own BOUNDARY section (`:179`) is consistent with this. No contradiction.

**Q6 Best version improvement:** Add a small companion Python script (this skill currently has none besides the kernel) that takes the extracted invoice/contract/PO/timesheet line arrays as structured input and runs the full PASS_2 through PASS_4 matching/verification/rollup loop in one code-execution call, invoking `verify_line_math()`/`escalate()` internally per line, instead of requiring the model to iterate and call the kernel per invoice line in-context. This is the biggest concrete runtime-cost fix in the group: it would turn an O(n) per-line model-turn loop into a single deterministic batch pass, which matters most here because invoice populations are the largest-N input of any skill in this group.

## Cross-cutting notes

- Kernel wiring quality varies sharply within the group: pro-forma-builder and invoice-rate-card-auditor wire the kernel tightly for all numeric outputs the kernel covers (with invoice-rate-card-auditor adding a dedicated fail-closed guardrail, G11). Commercial-negotiation-prep, should-cost-builder, and market-rate-benchmarking wire the kernel only for a subset of their numeric surface (escalation/percentile/quadrature/weighted-score) and leave rollup percentages, summary tables, and gap dollar amounts to prose.
- Two fully-built, self-tested generator scripts are orphaned: `should_cost_generator.py` (1763 lines) and `market_rate_generator.py` (1620 lines) are never named or called anywhere in their respective SKILL.md files, confirmed by full-text grep. Only `pro_forma_generator.py` is actually wired via an explicit HARD RULE. This is the single largest gap in the group: real code exists to make should-cost-builder and market-rate-benchmarking's xlsx outputs deterministic and reconciliation-checked the way pro-forma-builder's already are, and it is simply not invoked.
- The three research-heavy skills (commercial-negotiation-prep, should-cost-builder, market-rate-benchmarking) all impose a per-rate-line or per-cost-driver web-search multiplier (3+ searches per line/driver) with no batching; invoice-rate-card-auditor instead imposes a per-invoice-line model-reasoning loop with no batch/code-execution shortcut. None of the five skills define a hub-dashboard output slice; all are standalone deliverable owners.
